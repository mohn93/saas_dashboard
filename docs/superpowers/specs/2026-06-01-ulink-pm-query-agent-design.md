# ULink PM Query Agent — Design

**Date:** 2026-06-01
**Status:** Approved (pre-implementation)
**Location:** `flywheel_saas_dashboard` (Flywheel Command Center)

## Problem

The PM needs to query ULink's database to answer product questions, but should
not be handed Supabase dashboard access (which exposes API keys, secrets, auth
config) or any write/admin capability. We want a natural-language interface that
lets the PM ask data questions and get answers, while keeping the blast radius at
"reads only" and keeping user PII off third-party LLM providers.

## Solution Summary

A chat section inside the existing `flywheel_saas_dashboard` where the PM asks
questions in plain English. An LLM turns each question into a single read-only
`SELECT` against ULink's database. The query runs under a locked-down read-only
Postgres role, and the dashboard renders the results as a table + chart. Query
**results never go back to the LLM** — only the schema, the question, and trusted
examples are ever sent out. Successful queries can be promoted (by PM thumbs-up)
into a growing library of trusted examples that make the agent smarter over time.

### Key decisions (locked)

| Decision | Choice |
| --- | --- |
| Query model | Free-form `SELECT` generated by the LLM, executed under a read-only role |
| DB scope (v1) | ULink only |
| Result handling | Render rows (table + chart); **no** LLM summarization of results |
| Schema access | Auto-introspect; the read-only role's GRANTs are the real boundary |
| Agent loop | Bounded retry (self-correct on SQL error, ~3 attempts) + follow-up context |
| Memory | Capture every successful query as `unverified`; promote to `trusted` on PM 👍 |
| LLM provider | Behind a thin interface; default DeepSeek (OpenAI-compatible), swappable |

## Architecture

Follows the dashboard's established patterns (integration layer → API route →
client hook; `@/*` → `./src/*`).

- **`src/lib/integrations/ulink-agent/`** — new integration module
  - `client.ts` — node-postgres pool for ULink (read-only role) + the `LLMClient`
  - `introspect.ts` — reflect ULink schema into the catalog
  - `validate.ts` — SQL safety validator (security-critical)
  - `loop.ts` — the bounded generate→validate→execute→retry loop
  - `memory.ts` — read/write schema catalog, examples, query log (dashboard DB)
- **`src/app/api/agent/query/route.ts`** — orchestrates one question through the loop
- **`src/app/api/agent/feedback/route.ts`** — records 👍/👎, promotes examples
- **`src/app/api/agent/schema/refresh/route.ts`** — re-introspect on demand
- **`src/app/(dashboard)/agent/page.tsx`** + components — chat UI
- **`src/hooks/useAgentQuery.ts`** — client hook (loading/error/result state)

Auth reuses the existing Firebase session cookie + `ALLOWED_EMAILS` middleware.
Adding the PM = adding their email to `ALLOWED_EMAILS`.

## The Query Loop (Approach B — bounded retry)

1. **Table selection.** LLM receives the list of table names + their one-line
   descriptions (cheap) plus the question, and returns which tables it needs.
   This keeps prompts lean instead of dumping all ~50 ULink tables every call.
2. **SQL generation.** LLM receives full columns/types/FKs for *only the selected
   tables*, the top `trusted` example pairs, and the question. It returns:
   - one `SELECT` statement, and
   - a chart spec: `{ type, xColumn, yColumn }` (metadata only — no row data).
3. **Validate** (see Safety). Reject non-conforming SQL; inject/cap `LIMIT`.
4. **Execute** under the read-only role with `statement_timeout` and a row cap.
5. **On error**, feed the DB error message back to the LLM to self-correct.
   Repeat from step 3, up to 3 total attempts, then surface the error to the PM.
6. **Render** the table + chart. Show the generated SQL in a collapsible block so
   it is auditable. Offer 👍/👎.

Follow-up questions reuse prior turns as conversation context (e.g. "now break
that down by month"). The DB side remains stateless and read-only throughout.

## Database Access (the security boundary)

- A dedicated **read-only Postgres role** (`pm_readonly`) on ULink's database,
  connected via **node-postgres** over the Supabase **session pooler** — *not*
  the service-role REST client, which cannot run arbitrary SQL and is not
  read-only.
- The connection sets `default_transaction_read_only = on` and a per-statement
  timeout (e.g. 15s).
- The role's `GRANT`s are the allowlist. Introspection reflects exactly what the
  role can `SELECT`, so revoking a table at the DB removes it from both the
  schema catalog and the query path — one control point, no app-code drift.
  (v1: full `public` schema is in scope, per the chosen schema-access decision.)
- New env var: `ULINK_READONLY_DATABASE_URL`.

### Read-only role setup (DB-side prerequisite)

```sql
CREATE ROLE pm_readonly LOGIN PASSWORD '<strong-generated-password>';
GRANT CONNECT ON DATABASE postgres TO pm_readonly;
GRANT USAGE ON SCHEMA public TO pm_readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO pm_readonly;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO pm_readonly;
```

## Schema + Memory Subsystem

The dashboard has **no Postgres of its own** (its allowlist is the `ALLOWED_EMAILS`
env var and its cache is Upstash Redis). So agent memory is stored in a dedicated
**`pm_agent` schema inside ULink's existing Supabase**, written and read via the
**service-role** REST client (`ULINK_SUPABASE_SERVICE_KEY`) the dashboard already
uses for metrics. This is deliberately separate from the read-only `pm_readonly`
query path: the agent never writes through the query path, and never reads memory
through the read-only role. Three new tables (all in schema `pm_agent`):

- **`agent_schema_catalog`** — introspected structure (table, column, type, FK)
  plus an editable one-line description per table/column. Refreshed on demand or
  after migrations via the refresh route. **Reflected, not learned incrementally**
  — structure is exact and free from the Postgres catalog.
- **`agent_examples`** — `question → validated SQL` pairs. `status` is
  `unverified` on capture and becomes `trusted` only on PM 👍. **Only `trusted`
  entries are used as few-shot context** — the agent never learns from its own
  unverified output.
- **`agent_query_log`** — every question, generated SQL, attempt count, row count,
  success/fail, and requesting user. Serves as audit trail, debugging aid, and the
  source feed for `agent_examples`.

**Example retrieval (v1):** pass all `trusted` examples (few early on) + the
selected tables' details. **Scaling path (not built now):** pgvector similarity on
the question text when the trusted set grows large.

## Safety / Guardrails

The SQL validator is the security-critical component and must:

- Accept only a **single statement** that is a `SELECT` (or read-only `WITH ...
  SELECT`). Reject `INSERT/UPDATE/DELETE/MERGE/TRUNCATE`, any DDL, and
  data-modifying CTEs.
- Reject multiple statements (semicolon smuggling) and comment-smuggled writes.
- Inject a `LIMIT` if absent and cap it at a maximum (e.g. 1000 rows).

Defense in depth beyond the validator:

- `default_transaction_read_only = on` on the connection — a write would error at
  the DB even if the validator were bypassed.
- `pm_readonly` lacks write/DDL grants — third layer.
- `statement_timeout` bounds runaway queries.

## UI

New `(dashboard)/agent` section, dark theme, consistent with shadcn/ui + Tremor:

- Chat input + threaded conversation for follow-ups.
- Per answer: result **table**, **Tremor chart** from the chart spec, a
  **collapsible "View SQL"** block, and **👍/👎** controls.
- 👍 promotes the underlying `agent_examples` row to `trusted`.

## Testing

Vitest is configured (`npm test`).

- **SQL validator** — test hard: rejects DML/DDL, multi-statement, comment-
  smuggled writes, writing CTEs; accepts valid SELECTs; enforces the LIMIT cap.
- **Table selection & example retrieval** — unit-test with a stubbed `LLMClient`.
- **Read-only role** — verified once manually: attempt an `UPDATE`, confirm the DB
  rejects it.

## Out of Scope (YAGNI for v1)

- LLM prose summaries of results (privacy + scope).
- Multi-product support (PushFire, Somara).
- Any write capability.
- pgvector example retrieval.
- Chart editing / customization beyond the suggested spec.

## Prerequisites (outside the app)

1. Create the `pm_readonly` role on ULink's DB and grant `SELECT` (script above).
2. Add `ULINK_READONLY_DATABASE_URL` and `DEEPSEEK_API_KEY` to the dashboard env.
3. Add the PM's email to `ALLOWED_EMAILS`.
